MEDIUM PRIORITY — Architectural / Correctness

1. validateMatchingInterfaces Is Overly Conservative for Same-Mesh Asymmetric
   Leaf Selection
   File(s): src/basis/VectorConformingHierarchicalMultiPatchSplineSpace.cpp
            validateMatchingInterfaces()
            src/topology/HierarchicalMultiPatchCombinatorialMap.cpp
            initializeConstituents()

   Status (2026-09-29): IN SCOPE for the trace-infrastructure unification work.
   Arbitrary same-mesh refinement across patch interfaces must operate correctly
   before that work is considered complete. The unified trace layer is not to be
   landed with this limitation outstanding. Related: items 7 and 10.

   The current implementation requires that the leaf element sets on both sides
   of every patch interface match exactly at every refinement level. This rejects
   the mathematically valid case where:
     - Both patches have the same knot vectors at every level (conforming meshes)
     - Only the leaf element selection is asymmetric at the interface

   In a THB-spline basis, a merged interface function has support on both patches.
   If one patch is not refined at the interface, the merged coarse function's
   support is not fully covered, so it should remain active. The expected behavior
   is that fine-level merged DOFs adjacent to an unrefined neighbor are pruned
   while the coarse merged function remains active. The current activeFuncs()
   logic appears structured to produce this behavior, but the vector-conforming
   path rejects the configuration before it can be tested.

   Second gate: MEASURED ABSENT (2026-09-29). This entry previously recorded a
   coercion in the HierarchicalMultiPatchCombinatorialMap constructor as a
   second gate that would rewrite leaf status before validation ran. Experiment
   A disproves that for the same-mesh asymmetric case: the requested and
   effective leaf sets are identical at every level, dart set for dart set (see
   PHASE 0 RESULTS). Whatever coercion code exists does not fire for this
   configuration. Item 1 therefore has a single gate WITHIN THE TESTED SCOPE, in
   the vector-conforming path. Relaxing that validation makes the configuration
   CONSTRUCTIBLE only. It does not establish that active-function pruning or
   extraction is correct across the asymmetric interface, and that correctness -
   not constructibility - is the substantive content of item 1.

   Action:
     a. DONE (2026-09-29, Experiment A). leafElements() returns the requested
        leaf sets unchanged, so the rejection is not coercion-induced. This is a
        validation relaxation, not a topology-policy change. The scalar H1 space
        builds; only the vector-conforming builders reject the configuration.
     b. No coercion relaxation appears to be required. Re-confirm in 3D and with
        more than two patches before closing this sub-step.
     c. Relax validateMatchingInterfaces to permit asymmetric leaf selection when
        both patches share the same underlying mesh structure at all levels.
     d. Add an ALGEBRAIC test verifying: coarse merged interface DOF active,
        fine interior DOFs active, correct DOF count, and that the extraction
        operator includes the coarse merged DOF contribution on the fine
        patch's interface elements. Algebraic evidence only - extraction rows
        and connectivity, no quadrature. This step completes long before any
        physical trace machinery exists.
     e. Defer PHYSICAL H(div)/H(curl) trace conformity to Phase 7, once the
        evaluator and quadrature exist. State the H(div) check explicitly as
        (u_A . n_A) + (u_B . n_B) = 0 on the shared interface. Do not cite this
        as evidence for (d).
     f. Once (a)-(e) hold, cross-patch coarse-fine interfaces become
        representable and must be enumerated by patchTraceMeshInterfaces
        alongside the same-patch work in item 7.

   Note: This change requires careful verification of the THB-spline extraction
   across the asymmetric interface before merging.

   Note: The scalar HierarchicalMultiPatchSplineSpace performs no interface
   validation (level-count and constituent-count checks only), so the scalar and
   vector paths currently disagree about which configurations are legal.


2. Per-Element DOF Alignment at Flipped Multi-Element Patch Interfaces
   File(s): src/basis/TraceMesh.cpp  traceInterfaceElement()
            src/basis/MultiPatchSplineSpace.cpp
            src/topology/MultiPatchCombinatorialMap.cpp
            src/basis/VectorConformingMultiPatchSplineSpace.cpp
            test/Phase0_Characterization_test.cpp

   Status (2026-09-29): MEASURED. The defect is larger and differently located
   than this entry recorded. It is not merely that trace side data omits a
   permutation: the DOF merge and the element pairing use OPPOSITE conventions.

   Measured (Experiment B). patchTraceMeshInterfaces pairs elements correctly
   under Flip1d, i.e. reversed: element t=0 on patch 0 pairs with t=N-1 on
   patch 1. The merge does not follow suit - patch 1's tangential function k is
   merged with patch 0's function k rather than N-1-k. On a mirrored asymmetric
   interface (patch 0 t-element sizes [1,2] against patch 1 [2,1]) the merge
   still glues patch 0's size-1 element to patch 1's size-2 element, and
   construction nonetheless succeeds. Consequence: a paired element shares 1 of
   3 functions on a palindromic fixture, 2 of 3 on the mirrored asymmetric one.

   Separately, traceInterfaceElement applies no permutation at all when building
   TraceInterfaceElement, so even with a corrected merge the trace column order
   would still require alignment, and TraceSideData carries no ordering field in
   which to express it.

   Scope is wider than Flip1d. The four 3D permutations involve axis swaps.
   Measurement shows ZeroToOne and ZeroToThree agree under neither identity nor
   reversed column order, and ZeroToTwo agrees for H1 under full column reversal
   but not for H(div) or H(curl) - vector spaces need sign and direction
   handling in addition to reordering.

   Why the suite did not catch this: compatibleKnotPatterns compares knot
   patterns under reversal but never inspects the merge, and every existing
   fixture uses a palindromic interface knot vector, under which the identity
   and reversed merges coincide.

   Action:
     a. SETTLED: Flip1d reversal is authoritative and the function-ID merge is
        the inconsistent component. No convention decision remains.
     b. Localize the identity merge to MultiPatchCombinatorialMap dart
        identification or to the spline-space function-id merge. This determines
        whether the fix is topological or basis level.
     c. Fix it, using a non-palindromic interface fixture as the regression test.
     d. Only then align trace column ordering, adding an explicit ordering field
        to TraceSideData.

6. traceHasBrokenRows Performance
   File(s): src/basis/TraceMesh.cpp  interiorTraceMeshInterfaces()

   The Broken mode filter calls traceSideData() (which calls extractionOperator())
   for every interior face candidate. For large meshes this is O(n_faces) full
   extraction operator evaluations. A more efficient approach would inspect knot
   vector multiplicities directly to determine continuity statically.
   Not a correctness issue; relevant for large Navier-Stokes convergence studies.


7. Same-Patch Coarse-Fine Interior Trace Enumeration Is Deferred
   File(s): src/basis/TraceMesh.cpp  interiorTraceMeshInterfaces()

   Phase 5A enumerates same-patch, same-level leaf interfaces. It intentionally
   skips coarse-fine same-patch subdivision. This is acceptable for the current
   algebraic trace enumeration layer, but Phase 5B physical trace integration
   will need explicit quadrature-side subdivision if weak terms are assembled on
   coarse-fine interior faces.

   Action: Before using TraceMesh for DG/Nitsche-style same-patch hierarchical
   interior terms, add coarse-fine interface enumeration or a face-subdivision
   layer that maps fine trace quadrature points into the neighboring coarse side.

   Before implementing Phase 5B, the C++ API contract for TraceSpaceEvaluator
   must be written down explicitly:
     caller provides:  TraceSideData or ElementSide, side-local parent point,
                       geometry evaluator / control points
     returns:          side basis values, optional Piola-transformed basis,
                       normal/tangential trace components, outward normal,
                       tangent frame, side measure / Jacobian
     interface variant: paired side evaluations, mapped quadrature coordinates,
                        orientation/permutation metadata
   TraceSpaceEvaluator should wrap (not reimplement) SplineSpaceEvaluator.


9. 3D Tangent Frame Convention for H(curl) Traces (Phase 5B)
   In 3D, a face has one outward normal and two independent tangential directions.
   For H(curl) conforming traces both tangential components must be handled. The
   convention (ordering and normalization of the two tangent vectors, consistency
   with TPPermutation across interfaces) must be documented before implementing
   3D H(curl) physical trace tests.


10. Nonmatching Interface / Mortar Framework (Long Term)
    True asymmetric patch interface refinement where the two sides have different
    mesh structures (not just different leaf selections) requires mortar/Nitsche
    machinery: coarse-to-fine trace constraint matrices, Piola-aware trace
    transfer, and hierarchical truncation across patch interfaces. This is out of
    scope for the current strongly-conforming H(div)/H(curl) layer.


11. Python / API Exposure (Phase 6)
    NavierStokesMultiPatchDiscretization, NavierStokesHierarchicalMultiPatchDiscretization,
    buildL2MultiPatch, externalTraceDofs, interfaceTraceElements, and the new
    TraceMesh enumeration functions are not yet exposed in SplinesAPI.cpp.
    H(curl) spatial evaluation exists in C++ but likewise has no dedicated Python
    discretization/API path. Defer these bindings until the Phase 5B C++ layer and
    tests are stable.


12. Degree-Elevation and Knot-Insertion Scope
    Exact univariate and tensor-product transfer operators are implemented in C++.
    Tensor-product degree elevation is tested for surfaces and volumes, and nested
    knot insertion/refinement supports up to three tensor-product directions.

    Current high-level limitations:
      - globallyPElevate exposes only 2D tensor-product surfaces in Python.
      - globallyHRefine exposes uniform n-adic refinement only for 2D
        tensor-product surfaces in Python.
      - Arbitrary nested knot insertion is available through the C++ refinement
        operators but is not directly exposed as a Python transfer operation.
      - Multipatch and hierarchical p-elevation are not implemented as high-level
        operations.
      - Degree reduction, knot removal, cell merging, coarsening, and
        smoothing/roughing remain future Bezier-projection operations.

    These limitations do not affect the currently tested exact global transfer
    operations. Address them incrementally with the future Bezier-projection
    framework rather than by adding unrelated special cases to the existing API.

CURRENT CAPABILITY BOUNDARIES AND INTENTIONAL NON-GOALS
-------------------------------------------------------------------------------

A. Rational Analysis Spaces Are Intentionally Unsupported
   File(s): src/eval/SplineSpaceEvaluator.cpp  NURBSSpaceEvaluator

   The supported compatible-IGA formulation uses:
     - Polynomial B-spline differential-form spaces for the parametric H1,
       H(curl), H(div), and L2 de Rham sequence.
     - A B-spline or NURBS geometry map.
     - Pullbacks/Piola transformations to transport the polynomial analysis
       complex to the physical domain.

   NURBSSpaceEvaluator therefore implements manifold, Jacobian, Hessian, and
   parametric-to-spatial geometry evaluation. Its generic analysis-basis methods
   intentionally throw. This is a deliberate separation of geometry from
   analysis, not an unfinished prerequisite for the current de Rham framework.

   Compatible rational differential-form constructions do exist in the
   literature, including the Hiemstra-Huijsmans-Gerritsma partition-of-unity
   construction. That method derives weight-dependent rational edge, face, and
   volume functions; it is not obtained by merely evaluating the ordinary NURBS
   basis in every space. Supporting it would require a separate rational
   compatible-space family, derivative/incidence operators, refinement rules,
   and multipatch/hierarchical theory.

   Decision: A Hiemstra-like rational compatible analysis framework is not
   anticipated for sweeps. NURBS will remain a geometry representation, while
   compatible analysis will use polynomial B-spline spaces. Do not treat the
   intentionally throwing rational analysis methods as an outstanding defect.


B. Piola Evaluation Assumes Equal Parametric and Spatial Dimensions
   The implemented H1, H(curl), H(div), and L2 spatial values/first derivatives
   are tested for 2D planar domains and 3D volumetric domains, including curved
   geometry and nonuniform knot spans. They require a square
   parametric-to-spatial Jacobian.

   Embedded-manifold transforms, such as a two-dimensional analysis space mapped
   into three-dimensional space, are not supported by these routines. Physical
   normal/tangential trace values, side measures, and paired-interface
   evaluations are also not supplied by the volume evaluator; those belong to
   Phase 5B and the TraceSpaceEvaluator contract in items 8 and 9.


C. Strong Multipatch Coupling Uses Matching, Unscaled Interface Charts
   Current strong H1/H(curl)/H(div) merging supports compatible interface knot
   structure together with coordinate permutations, orientation reversals, and
   origin translations. Interface parameter scaling is rejected because the
   union-find DOF identification can represent equality and orientation signs,
   but not weighted constraints.

   Same-mesh asymmetric hierarchical leaf selection is the valid extension in
   item 1. Truly nonmatching interface meshes or scaled transition maps require
   the weak/mortar framework in item 10 and are not defects in the current strong
   coupling implementation.


D. Broken L2 Spaces Work; Physical Interior-Face Assembly Is Deferred
   Reducing a degree-p C0 H1 direction preserves interior multiplicity p while
   reducing the degree to p-1, producing C-1 L2 connectivity. This is supported
   within single patches and in multipatch/hierarchical constructions. The
   corresponding RT/Nedelec mixed primal/reduced continuity patterns are also
   supported.

   Element-local evaluation and algebraic broken-face enumeration work now.
   DG/Nitsche-style integration still requires Phase 5B physical trace evaluation;
   hierarchical coarse-fine interior faces additionally require the subdivision
   work in item 7.
